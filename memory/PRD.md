# Xaluca Tours — PRD / Estado

## Problema original
App full-stack (React + FastAPI + MongoDB) para agencia de viajes a medida por Marruecos, heredando el sistema de diseño premium "Grup Xaluca" (Dark Academia, zellige, acentos dorados #D4A373). Trilingüe (es/en/fr), mapas Leaflet, CMS global editable por slots, audio global persistente, notificaciones por email (Resend), galería Pexels/Unsplash, precios por ruta.

## Arquitectura
- backend/server.py — CMS slots, leads CRUD, files, integraciones, Resend
- frontend/src/lib/{routes.js, routeComponents.js, allTripsCatalog.js, pricing.js, programPricing.js, preciosData.js, homeCarousels.js}
- frontend/src/pages/{PreciosPage.jsx, AdminPage.jsx}
- Idioma por defecto (es) en raíz; en/fr bajo /<lang>/<slug>

## Implementado (jun 2026)
- **Warm-up de caché de imágenes para TODAS las imágenes (jun 2026) — COMPLETADO + TESTEADO (iteration_49 + self-test)**:
  - Objetivo: que incluso la primera visita "fría" cargue al instante (sin coste de codificación AVIF en el primer request) para todas las imágenes.
  - Backend: pre-genera variantes AVIF+WebP (anchos `WARM_WIDTHS=[24,768,960]` — LQIP + los anchos que eligen las galerías de día) de cada imagen en `db.files`, escribiéndolas en la caché de disco (`/app/backend/img_cache`). Usa un **ProcessPoolExecutor** (contexto `spawn`, `cpu-2` workers) con `_encode_all_variants` (decodifica la original una vez, 1 envío IPC por imagen) para paralelizar el encode CPU-bound. Idempotente (salta variantes ya cacheadas). Se lanza solo en background al arrancar (delay 20s) y bajo demanda. Endpoints `POST/GET /api/admin/warm-image-cache[/status]` (Bearer admin). AVIF `speed=8` (encode más rápido, calidad ~igual).
  - Frontend: panel `WarmCachePanel` en la pestaña "Mirror DB" del admin ("Optimizar todas las imágenes") con botón + barra de progreso en vivo (polling cada 1.5s). FIX (iteration_49): el polling ahora se liga a `status.running` vía useEffect, de modo que el progreso se actualiza tanto si lo lanza el botón como si el warm-up ya venía corriendo desde el arranque (botón deshabilitado). Auto-verificado: el progreso avanza solo sin interacción.
  - Resultado: variantes servidas desde caché en ~5ms (AVIF 8.6KB) / LQIP 365B en ~1.6ms. Cubre LQIP + galerías de día; héroes/retina (eager, pocos) se codifican bajo demanda y quedan cacheados. Nota: la caché de disco es efímera (se regenera tras un redeploy; el warm-up se relanza solo al arrancar).
- **Blur-up (LQIP) en galerías de día — fin del placeholder negro (jun 2026) — COMPLETADO + TESTEADO (100%, iteration_48)**:
  - BUG: en carga "fría" las imágenes de día tardaban (fetch del original + encode AVIF) y mientras tanto el contenedor `bg-[#1A1513]` mostraba NEGRO. Las galerías dinámicas usaban `<Img>` (un `<img>` desnudo sin placeholder), de ahí el negro; `EditableImage` ya tenía shimmer cálido.
  - FIX (blur-up): nuevo helper `lib/imageUrl.js#lqipSrc(url)` = `optimizedSrc(url, 24)` → miniatura LQIP diminuta (~365 bytes AVIF). `Img.jsx` ahora es stateful: mientras carga aplica la clase `.img-blurup` + `backgroundImage` inline con el LQIP (desenfocado por CSS), y al `onLoad` añade `is-loaded` (quita el blur y el background). `EditableImage`/SmartImage usa el mismo LQIP sobre su `cms-img-fade` (sustituye el shimmer cuando la fuente es optimizable). CSS `.img-blurup` en `index.css`: `blur(16px)`→`blur(0)`, fallback `background-color:#2b2622` (marrón cálido, nunca negro). Backend `download_file`: buckets de ancho ahora incluyen **24 y 48** para servir LQIP reales (~24px).
  - Resultado: la imagen aparece al instante como preview suave y se nitidiza progresivamente; sin negro, sin CLS (el visor reserva su aspect-ratio), lazy bajo el fold + eager/`fetchpriority=high` en `priority`. Verificado por testing agent bajo throttling 250KB/s en 2 itinerarios: visor + miniaturas con blur-up, 0 imágenes rotas, navegación next/prev conserva el efecto.
